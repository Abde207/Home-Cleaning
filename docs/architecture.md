# Architecture

Source of truth: [master specification](../Home_Clean_App_Complete_Design_Until_Phase_12A.md). Supporting UML: [existing reference](../home_clean_app_uml_design_complete.md). Current implementation/validation: [status](codex-implementation-status.md).

Separate Flutter customer/provider shells and a Next.js admin shell target a NestJS modular monolith over `/api/v1`. PostgreSQL/Prisma owns transactional data. Redis currently supplies authentication rate limits. The scoped PostgreSQL-polling Dispatch worker is validated; notification delivery and other queues/workers remain specified. Clients have no direct database access.

PaymentModule extends the existing Booking finance boundary with a provider abstraction, local mock adapter, payment attempts/history, HMAC-verified webhook processing, refunds, cash attribution/reconciliation and separate settlement commands. Booking remains the owner of Booking state transitions; settlement records remain separate from customer Payment records. A real external provider adapter is not claimed.

LocationModule owns address validation/default selection and a credential-free deterministic geocoding provider used in local/test environments. Company service areas remain center/radius records and Dispatch remains the sole eligibility/scoring policy. Team location updates are explicit, row-locked reports; stale locations fall back to service-area centers and are not continuously tracked.

NotificationModule consumes durable OutboxEvent records, creates event-keyed user notifications, registers multiple owned device tokens, and delivers through a push-provider abstraction with mock delivery, retry/backoff, append-only delivery attempts and invalid-token cleanup. Notifications are projections of authoritative state and never write Booking, Payment or Settlement truth.

ProviderAssignmentsModule is the provider operational read boundary. It applies the existing persisted `assignmentScope` to every list/detail and projects only safe Booking snapshots, target company/team identity, server-derived job action capabilities, append-only completion-proof metadata and role-authorized cash state. Managers read their active company assignments; cleaners read their exact active team. The module does not own assignment transitions: accept/reject/job execution/no-show/proof/cash commands remain Booking-owned with the existing locks, idempotency, history and audit. `GET /provider/cash-worklist` is cleaner-only and reads Payment/CashCollection truth.

Phase 13C exposes those existing commands through the Provider Flutter layers. `TEAM_ACCEPTED → TEAM_ON_THE_WAY → CLEANING_STARTED → CLEANING_COMPLETED` remains the sole operational graph; Assignment remains `ACCEPTED` until operational completion and then becomes `COMPLETED`. Start revalidates the persisted company/team and service capability under lock. Completion proof remains immutable metadata referencing external storage; no upload system is simulated. Cash collection locks the authoritative Payment and uses its exact amount. Provider completion does not bypass finance: reconciliation and final Booking `COMPLETED` remain Payment/operations commands. Every client command refreshes the scoped provider detail, and transport retries retain the same idempotency key.

## Implemented backend

DatabaseModule exports PrismaService, which connects/disconnects through Nest lifecycle hooks. RedisModule owns a client with bounded timeouts. ConfigModule validates dependency URLs, port, CORS and OTP settings. Bootstrap configures DTO validation, response/error envelopes, request IDs, metadata-only logs, Helmet and CORS.

AuthModule issues opaque access/refresh tokens with hashes persisted in PostgreSQL. OTP verification locks its database row. Refresh/logout serialize token-family operations with PostgreSQL advisory locks. The global guard checks session expiry/revocation, active identity and current role/company/team scope on protected requests. Public routes require explicit metadata.

CoreModule contains thin customer/catalog/provider/admin controllers backed by CustomersService, UsersService, CatalogService, AdminCatalogService, CompaniesService and TeamsService. BookingModule adds BookingController and BookingService over the existing Booking/history/payment/idempotency tables. Address/property operations share the customer ownership boundary. PrismaService remains the persistence adapter. Explicit query projections define responses. Privileged catalog/company/team/identity/booking writes and their audit records share transactions; mutable records use row locks, Booking command retries use an actor/operation/key advisory lock, and provisioning uses a phone advisory lock. Booking snapshots are captured from current Core Domain records at creation and are never recomputed from mutable profiles/catalog data.

## Booking boundary architecture

Booking owns the state machine and is the only module allowed to change Booking status. Commands are explicit and transactional: quote handoff, online/cash payment confirmation, assignment handoff, provider job transitions, no-show outcomes, proof metadata, cash collection, reconciliation, completion and refunds. There is no generic status update route.

The Pricing boundary validates a trusted quote against the existing append-only `BookingPriceSnapshot`; it does not rewrite history. Payment boundaries persist separate Payment, PaymentEvent, PaymentTransaction, CashCollection and Refund records. Assignment boundaries persist Assignment, AssignmentEvent, DispatchAttempt and CompletionProof records and enforce the existing company/team authorization scope. All commands use Booking/Assignment row locks plus actor-operation-key advisory idempotency.

PricingModule evaluates validated versioned rules over the existing Decimal catalog baseline and applies fixed-amount promotions. `POST /bookings/quote` persists an immutable, owner-scoped PricingQuote containing source/extra/price/rule/promotion snapshots and expiry. Rule publication/activation is serialized against quote evaluation; each evaluated line uses two-decimal HALF_UP rounding. Customer responses omit provider commission data.

BookingModule imports PricingModule. Booking creation consumes a supplied quoteId exactly once or issues/consumes a current quote inside the same transaction for existing callers. Quote ownership, input equality, expiry, current resource activation and promotion capacity are checked before copying historical values into Booking and BookingPriceSnapshot. QuoteConsumption enforces unique quote/booking linkage and matching owners. Promotion redemption, consumption, Booking/history/snapshots, audit and idempotency are atomic. Booking still starts REQUESTED and confirmation remains an explicit Booking command.

Additive migration 0004 creates quote persistence/consumption and protects quote/rule/promotion history. It is applied to the configured public schema and recorded with a matching checksum in Prisma's migration ledger. See [Phase 7 contract and policy decisions](phase7-pricing.md).

DispatchModule now provides the initial candidate-selection boundary and calls BookingService's transactional `dispatchOffer` handoff. Booking still exclusively owns status transitions, Assignment writes, history and human-command idempotency. Dispatch reads Team/Company schedules, service capabilities, radius areas, current overlap workload and historical assignment outcomes; it locks candidate Team rows in stable order and hands a ranked, auditable decision snapshot to Booking. The common offer writer rechecks team capacity under the same lock and prevents a second active assignment for the same booking. Configurable weights, speed/offer/retry limits and location freshness are snapshotted in DispatchAttempt.candidates; ETA is straight-line/area-center approximation, not a maps-provider route. Provider offer reads use assignmentScope and a narrow price-free projection. DispatchWorker polls database state every ten seconds outside test mode; its actorless internal Booking command uses null-actor audit/history and row-lock convergence rather than an invented user/session. OutboxEvent records offer/no-team and domain notification handoffs atomically, with delivery deferred to NotificationWorker. See [Phase 8 record](phase8-dispatch.md) and [Phase 11 record](phase11-notifications-location.md).

The compatibility `/bookings/:id/assign` route now enters DispatchService and the common Booking offer transaction. It requires a dispatcher/admin grant, idempotency key, nonblank reason, exact slot and future expiry, and shares area/availability/capacity policy and the narrow operational response with `/dispatch/bookings/:id/manual`. The former direct Booking manual writer was removed. Terminal no-team and accepted/started manual reassignment return explicit conflicts because the master Booking graph has no recovery edges. Separate-process workers converged, recovered after termination, avoided duplicate work after restart, and sustained timer retry/fault validation locally. Phase 8 Dispatch is complete for the scoped backend gate. The future payment gateway/webhook adapter, settlement, object storage, notifications, maps and production client flows remain separate dependencies.

After manual-policy hardening, `npm.cmd run test:unit` passes 32/32 and the exact `npm.cmd test` live suite passes 50/50 in a fresh four-migration PostgreSQL schema with Redis. Prisma child execution remains intermittent: other wrapper attempts stopped before assertions at schema-engine download refusal or installed-engine `spawn EPERM`. Seven configured database Pricing integrity checks passed at Phase 7; the existing 16 database integrity assertions passed previously on a disposable migrated schema. Native Prisma CLI status/deploy and the separate `test:database` wrapper remain environment-blocked before assertions. No application architecture was modified for this restriction.
