# Engineering Phase 8 — Dispatch backend

Updated 2026-09-21. **Complete for the scoped Dispatch backend acceptance.** Phase 7 Pricing remains complete. Flutter, payment gateway, settlement, notification and maps phases were not started.

## Existing boundary reused

The schema already had Company, Team, TeamAvailability, CompanyServiceArea, TeamServiceCapability, Assignment, AssignmentEvent and DispatchAttempt. BookingService already owned the booking state machine, provider accept/reject/job commands, assignment history, status history, audit and idempotency. No second assignment model or schema migration was added. DispatchModule selects a candidate inside BookingService's booking-locked transaction and hands the offer back to BookingService for the existing Assignment/history/state writes.

The compatibility `POST /bookings/:id/assign` now delegates to the same Dispatch manual selection and Booking transaction as `POST /dispatch/bookings/:id/manual`. Only an unscoped Home Clean dispatcher/admin grant with `dispatch:manage` can call either route; customers and provider company/team roles cannot. The legacy input retains `companyId`, `teamId`, `startsAt`, `endsAt`, and `expiresAt`, and now requires a nonblank 1–500 character `reason`; optional `overrideAvailabilityAndArea` has exactly the same limits as the new manual route. Its slot must equal the stored Booking slot and expiry must be in the future. Both routes return the narrow operational Booking projection (ID, booking number, status, schedule, assignment IDs/company/team/status/times), excluding price, payment and customer identity. Both require an `Idempotency-Key` and reject replay with changed input. The old direct Booking manual writer was removed, so it cannot bypass area/availability policy or the narrow response.

## Implemented slice

- `POST /dispatch/bookings/:id/offer`: dispatcher/admin-owned automatic decision. Booking must be payment-confirmed, searching, rejected, team-no-show or have an expired pending offer. A live pending offer cannot be replaced. Expired offers are marked EXPIRED with an AssignmentEvent and Booking history before a new search in the same transaction.
- Candidate eligibility considers active company/team and AVAILABLE status, service capability, a single positive availability window covering the full historical Booking slot, overlapping negative windows, active company radius area coverage, overlapping OFFERED/ACCEPTED workload versus team capacity, and distance/ETA. Current team location is used only when fresh; otherwise a covering area center supplies an explicitly approximate fallback. No maps-provider routing is claimed.
- Configurable weights score availability, service/capability, proximity, workload, reliability and completion performance. Ranking uses score descending, ETA ascending and team UUID ascending. The defaults and runtime settings are described below. Full policy, candidate factors, rejections, weights and selected team are stored in DispatchAttempt.candidates and assignment audit data.
- Previous team assignments for the booking are excluded on automatic retries. A configurable offer limit ends in NO_TEAM_AVAILABLE with a persisted attempt and audit event. Explicit follow-up dispatch calls after rejection or expiry can select the next team.
- `DispatchWorker` polls PostgreSQL every ten seconds outside test mode, finding payment-confirmed/searching/rejected/team-no-show bookings and expired pending offers. Separate-process validation through `scripts/validate-dispatch-processes.ps1` started independent Node workers against the same PostgreSQL/Redis environment: competing sweeps produced one offer, a parked worker was terminated during processing, a surviving worker recovered the booking, a restarted worker found no duplicate work, and sustained timer sweeps handled rejection retry, expiry retry and an injected outbox failure after the trigger was removed. The ten-second timer and recovery behavior are validated locally; this is not a production soak test.
- Each offered Assignment also writes an `ASSIGNMENT_OFFERED` outbox event in the same transaction; a no-team result writes `DISPATCH_NO_TEAM_AVAILABLE`. These are durable notification handoffs only—no push delivery or notification consumer is claimed.
- `POST /dispatch/bookings/:id/manual`: dispatcher/admin manual offer/reassignment while an offer is pending or booking is otherwise assignable. Requires a nonblank reason. An optional explicit override bypasses only availability and area/ETA gaps; it does **not** bypass active company/team, service capability, slot, team status or capacity. Failed selection rolls back cancellation of a prior offer. The offered assignment, DispatchAttempt policy snapshot, Booking status history, AssignmentEvent, actor-linked AuditLog and outbox are committed together. When replacing an offered assignment, its cancellation, event and audit include the operator reason.
- `GET /dispatch/offers` is provider company/team-scoped and returns only the operational offer projection: assignment/booking IDs, schedule/expiry, service name/duration, address/location and instructions. It omits prices, commission, customer identity and internal candidate scores. `GET /dispatch/monitoring` exposes operational counts and recent attempts only to dispatch:manage actors.
- Existing `/assignments/:id/accept` now rejects expired offers and non-operational teams, retaining provider resource scope, Booking row lock, history and idempotency. The common Booking offer writer locks the team and rechecks capacity, so policy selection and the legacy manual route cannot double-book a one-capacity team through concurrent offers.

Dispatch does not modify payment, quote, refund or settlement records. Customers still book through Home Clean; provider identities and internal scores are not exposed through the new provider offer API.

## Manual intervention and lifecycle contract

The master Booking graph makes `NO_TEAM_AVAILABLE` terminal, while its Dispatch prose calls for admin intervention without defining a reopening transition. The chosen contract is **review and resolve outside this booking's Dispatch lifecycle**: `POST /dispatch/bookings/:id/manual`, legacy `/bookings/:id/assign`, automatic offer and retry cannot reopen it. A manual offer returns 409 `DISPATCH_TERMINAL_NO_TEAM_AVAILABLE`; no new Assignment, DispatchAttempt, status history or outbox row is written. Operations can inspect monitoring, history and the no-team outbox handoff. Any future replacement-booking, payment or refund workflow needs its own defined authorization and state contract; this phase does not invent one.

The same graph has no edge from `TEAM_ACCEPTED`, `TEAM_ON_THE_WAY` or `CLEANING_STARTED` back to search. Manual offer/reassignment from those states returns 409 `DISPATCH_ACCEPTED_JOB_REASSIGNMENT_UNSUPPORTED`, keeping the accepted assignment and Booking state unchanged. The existing explicit `TEAM_ON_THE_WAY → TEAM_NO_SHOW → SEARCHING_FOR_TEAM` path remains available when a provider team actually does not show; it cancels the accepted assignment with history before a new offer. It is not a generic operator reassignment command. A new controlled reassignment path after acceptance or work start would require a separate Booking state-machine and operational/financial policy decision.

## Configuration and policy limits

Optional environment variables: `DISPATCH_WEIGHTS_JSON` (object with numeric weights `availability`, `service`, `capability`, `proximity`, `workload`, `reliability`, `performance`, each 0–100; at least one positive), `DISPATCH_OFFER_SECONDS` (1–3600, default 600), `DISPATCH_MAX_ATTEMPTS` (1–20, default 3), `DISPATCH_TRAVEL_KPH` (1–120, default 30), and `DISPATCH_LOCATION_MAX_AGE_MINUTES` (1–1440, default 120). `DISPATCH_WORKER_ENABLED=false` disables the background sweep; test mode disables its timer but can invoke `runOnce` directly. Default weights are 1/1/1/3/2/1/1 in that order. Invalid configuration fails service initialization. Weights and assumptions are snapshotted with each decision; production values require operational calibration. Straight-line ETA is an approximation until the Maps phase. Reliability/performance are derived from assignment outcomes, not external ratings. The existing capability model is service-level only; equipment/skill-specific eligibility has no underlying structured data yet.
